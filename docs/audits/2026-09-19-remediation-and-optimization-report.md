# Codex Web 整改与优化报告

审计日期：2026-09-18 至 2026-09-19（Asia/Shanghai）

代码基线：`23fb2a9`，扫描开始时工作区干净

范围：产品体验、视觉与交互、Web 性能、服务端性能、可靠性、权限生命周期、工程验证

## 1. 核心结论

**项目具备完整的可用基础，下一阶段最值得投入的是状态可靠性、大历史场景的响应速度，以及手机上的操作可见性。** 当前实现已经有事件重放、背压、请求去重、提交 outbox、缓存配额、触摸布局、焦点管理和自动化门禁。优化应该沿着现有架构做，保留 Mac 本地执行、单用户默认、可信团队和 SSE 的产品边界。

本次发现 **5 项已定向复现的功能缺陷、1 项已复现的草稿恢复缺口，以及多项有测量依据的性能与界面问题**：

- 切换会话时，旧请求的错误会清掉当前正常会话，造成“会话消失”的错觉。
- 历史消息加载失败没有清楚反馈，页面可以显示“就绪”却缺少历史。
- 兼容性回退只查询前 100 个线程，会使更早的会话“列表可见、详情打不开”。
- 在线服务与 CLI 并发操作认证文件时，改密结果可能被旧请求覆盖。
- 公开分享过期后，已经打开的 SSE 连接仍能接收新内容；仅影响显式启用的分享功能。
- 未发送草稿只存在内存，刷新页面后丢失。

性能热点也比较明确：**整页 DOM 重建、后端先全量读取再分页、同步 JSON 存储和锁等待**。在本次压力样本中，局部流式更新开销明显小于整页渲染，不能把卡顿笼统归因于“每个 token 都重绘整个页面”。

视觉上最先需要处理的是工作详情入口过小、摘要文字对比度不足、停止操作隐藏和中文设置拥挤。主题数量已经足够，主要收益来自层级、可读性和操作路径。

## 4. 已确认的缺陷与恢复缺口

### B1：旧请求失败会清理当前正常会话

**复现过程**：先打开 A，延迟 A 的 `/status`、`/timeline`；在响应前切到 B，确认 B 的文件和历史已经显示；再让 A 返回 `404 session_not_found`。

结果：B 从当前列表中消失，工作区恢复记录被清空，桌面自动选择了另一个会话，并显示“所选会话不可用”。被移除的是浏览器当前列表中的 B，**本次没有发生服务器上的会话删除**。

根因：`selectSession()` 的成功路径检查 `state.sessionId !== sessionId`，但错误路径先调用 `handleMissingSession()`；后者读取全局 `state.sessionId`，把 B 当成失败对象。`authRequestGeneration` 只隔离认证变化，无法隔离导航请求。

证据：`packages/codex-web/public/app.js:6175`、`:6196`、`:8644`。截图：[错误响应后的页面](2026-09-19-evidence/race-missing-session.png)。

整改：为会话打开建立独立 request generation 和 AbortController；成功、失败、finally 都验证请求归属；`handleMissingSession` 显式接收失败的 sessionId，只处理对应缓存和页面。

验收：A→B、A→B→A、进入新会话/文件查看时的乱序成功和 404/403/500，均不能破坏当前选择、草稿和事件连接。不要仅修补 404 分支。

### B2：历史接口失败，页面仍显示“就绪”

**复现过程**：已有历史的会话，`/status` 返回正常摘要，`/timeline?limit=50` 返回 500，浏览器没有该会话的历史缓存。

结果：页面显示首条问题预览和“就绪”，助手历史消失，没有“历史加载失败”或对应重试入口。服务器上的历史仍然存在。

根因：`loadSessionOpenData()` 把非致命错误转成 `{ok:false}`；只要 status 成功，就返回 `compact:true, timelineSource:'none'`。调用方随后清空错误并设置 Ready。首次打开也没有统一的请求截止时间；恢复和历史翻页各有超时，策略分散。

证据：`app.js:6234`、`:6288`、`:6313`、`:6219`、`:14640`。截图：[历史失败却就绪](2026-09-19-evidence/partial-history-error.png)。

整改：分开表达“执行状态”和“历史加载状态”；保留缓存时注明缓存/同步失败，无缓存时显示局部错误与重试。给首次打开设置有界超时，并保留 B1 的请求归属保护。仅对确实不支持 compact API 的情况回退完整接口，避免错误时无限增加请求。

验收：status/timeline 四种成功失败组合、离线、有缓存/无缓存、超时后返回、点击重试，都有明确状态；不得把缺失的历史默认为空历史。

### B3：兼容性回退漏掉第 101 个及以后的会话

触发条件：provider 的 `readThread` 返回 `list_turns is not supported yet`，且目标线程不在第一页。

合成 101 个线程时，`listSessions()` 正确取得 101 条；读取第 101 条详情却返回 `null`。调用记录显示回退只执行了 `listThreads({limit:100, archived:false})`，没有消费 `nextCursor`。

证据：`packages/codex-web/src/runtime.ts:1472`、`:1500`。本次只验证兼容分支，不能据此推断当前 Mac 的 Codex 版本一定触发此错误。

整改：回退应优先使用已有完整目录快照，必要时沿 cursor 查到目标；复用已有的循环 cursor 检查和请求合并。provider 能力不足与“线程不存在”应区分，不能把无法取得历史直接解释成删除。

验收：目标位于第 1、2、末页；空页但仍有 cursor；回退也失败；归档线程；缓存过期；并验证错误不会触发 B1。

### B4：在线改密存在跨实例 lost update

`AuthStore` 的锁是实例内 Promise。HTTP 服务和 `codex-web auth set-password` 各自创建 store，不能互相串行化。

定向交错实验：实例 A 在 `verifyToken()` 中读到旧认证状态后暂停；实例 B 完成改密并清空 sessions；A 恢复，把旧状态连同新的 `lastSeenAt` 写回。

**实验结果：旧 token 有效、旧密码仍可登录、新密码无法登录。** 实验使用两个实例和显式读后屏障模拟两个进程的交错，证明该读写协议存在缺口；没有测量线上自然发生概率。

证据：`auth_store.ts:62`、`:110`、`:204`；CLI 与服务构造入口 `cli.ts:229`、`:273`。现有原子 rename 能避免半文件，不能阻止读旧值再覆盖新值。

整改：立即统一认证写事务的跨进程锁；或者通过服务端单一写入口执行改密。加入认证版本并用条件更新保护 `lastSeenAt`，把密码变更与撤销全部旧会话放在同一事务中。F4 的降频写入应同时做，但不能只靠“减少写入概率”解决正确性。

验收：真实子进程并发改密、verify、login、logout；操作完成后旧密码和旧 token 永远不能因迟到写入复活。

### B5：公开分享过期没有终止现存 SSE

触发条件：多用户模式与 `CODEX_WEB_PUBLIC_SHARES_ENABLED=true` 均已开启，接收方在 TTL 到期前建立连接。

实验为测试 share 设置 1 秒 TTL。到期后新 GET 返回 404，但旧事件连接未关闭，仍收到到期后追加的 `assistant.delta`（`phase: final_answer`）。

根因：`handlePublicShareRequest()` 只在建立连接时检查 `expiresAt`；`streamTurnEvents()` 没有接收授权截止时间或持续有效性检查。

证据：`server.ts:2272`、`:2294`、`:7399`。撤销 share、关闭多用户模式已有关闭 SSE 的处理，本项是 TTL 到期路径的缺口，不能把既有撤销机制也描述为缺失。

整改：把授权截止时间绑定到 SSE 生命周期，到期销毁连接并停止投递；建立统一的会话/用户/角色/项目授权变更失效机制。后一部分目前主要是静态审查建议，应补独立回归验证。

验收：TTL 到期后不能再收到新事件；分享撤销、多用户关闭、用户禁用、项目撤权和登录退出均有明确的连接失效契约。保持公开分享默认关闭。

### B6：草稿只保存到内存

已复现：在空闲会话输入一段未发送文本，刷新后同一会话恢复，但输入框为空。切换会话时有内存草稿保存，提交后的 outbox 也有持久化；缺口是**尚未提交的输入**。

证据：`app.js:1044`、`:1048`、`:1061`、`:4598`，`promptDrafts` 是 Map。手机后台被系统回收的相似影响仍需真实设备验证，本次直接验证的是 reload。

整改：草稿按账户和 sessionId 持久化，防抖写入并在 pagehide 尝试刷新；明确新会话草稿、附件引用、退出登录、发送成功后的清理策略。避免跨账户恢复草稿。

验收：输入、刷新、离线重启页面、切会话、退出后换账户、发送失败/成功都有一致恢复结果。

## 5. Web 与服务端性能

### F1：整页重建是已测得的主要前端热点

`render()` 执行 `app.innerHTML = ''`，随后重建主界面、绑定事件、恢复输入框和滚动。`localizeElement()` 又序列化并重设 `innerHTML`。历史继续加载时，已读内容持续加入 `state.timeline`，没有对可见 DOM 建立固定窗口。

证据：`app.js:740`、`:2678`、`:12457`、`:13945`。局部动态更新已经有 `requestAnimationFrame` 合并和 dirty entry 更新：`:4982`、`:5003`、`:5180`。

在 390×844 触摸模式、4 倍 CPU 降速下，以实际渲染代码注入不同数量的合成中英文/Markdown 消息，测量同步渲染及布局读取：

| 可见消息数 | 样本总字符约数 | DOM 节点数 | 整页渲染观测范围 | 局部更新观测范围 |
| ---: | ---: | ---: | ---: | ---: |
| 4 | 2,759 | 179 | 7–41ms | 0.6–3.7ms |
| 100 | 68,420 | 5,267 | 104–119ms | 0.5–2.7ms |
| 500 | 342,220 | 26,467 | 506–560ms | 1.3–6.5ms |

每档进行 4 次整页渲染、5 次局部更新；这是压力实验，不是正常打开页面必然出现 500 条消息，也不是 INP 的正式采样。它证明用户持续加载历史后，后续整页操作会随 DOM 规模明显变慢。

整改顺序：

1. 设置、菜单、状态条、会话列表分别更新，保留 timeline 和 textarea 节点身份。
2. 消息历史采用有界窗口或虚拟化，保留上下滚动锚点；不能只分页取数据后永久堆积 DOM。
3. 稳定的最终消息缓存 Markdown 结果；国际化在模板生成时完成，避免 DOM→字符串→DOM 往返。
4. 为长历史下打开菜单、进入工作详情和输入操作增加性能回归。

### F2：列表和历史都是“全量读取后切页”

会话列表路径：`server.ts:872` 调用 `runtime.listSessions()`，`runtime.ts:474` 在 5 秒快照失效后扫描全部 provider pages，最后 `session_list_page.ts:30` 去重、排序、切片。5 秒缓存和 in-flight 合并已有，但冷请求成本仍随总会话数增长。

定向实验：请求 `/api/sessions?limit=30`，provider 有 1,000 条线程，**实际触发 10 次 provider list 调用才返回 30 条**。每次调用人为设置 10ms 延迟，整体约 138ms；此耗时只用于展示串行全量扫描成本，不代表真实 provider 延迟。

历史路径：`server.ts:977` / `:4318` 先 `runtime.readSession()`，其读取完整 turns 并组装 timeline，然后 `paginateSessionTimeline()` 切片。`limit=50` 限制响应体，不限制上游历史解析量。文件 resolve/content 也会先读取完整 session，见 `server.ts:910`、`:939`。

整改：

- 为目录建立轻量快照/索引，返回首屏后后台补全；活跃和待审批状态独立增量维护，避免为了全局置顶重新扫所有历史。
- 为时间线提供真正的分页读取接口；provider 缺少该能力时，维护按线程版本更新的本地投影索引。
- 文件授权和 cwd 获取走轻量元信息接口；避免为了下载文件再次解析整段对话。
- 保留 cursor 范围绑定、权限校验和活动项优先级，不能为提速破坏原有正确性。

验收重点是每页上游调用数、解析条目数、TTFB 与内存，而不只是响应 `items.length`。

### F3：同步 JSON 存储和同步锁占用服务主线程

`FileSessionTimelineStore` 的 list 会读取并规范化整个文件；append/replace 读整个文件、压缩、格式化序列化、写临时文件并 rename。settings store 也使用同步整文件读写。同步锁竞争通过 `Atomics.wait` 等待，默认最长 5 秒。

证据：`session_timeline_store.ts:60`、`:93`、`:122`、`:147`；`session_settings_store.ts:65`；`file_lock.ts:113`、`:161`。

合成 40 个 session、共 1,000 条本地 timeline 消息，7 次读取和 5 次追加的测量如下：

| 文本负载规模 | 查询单个 session 的中位耗时 | 追加 1KB 的中位耗时 |
| ---: | ---: | ---: |
| 1MiB | 0.85ms | 5.49ms |
| 8MiB | 4.70ms | 26.93ms |
| 15MiB | 8.33ms | 48.12ms |

这是本地额外 timeline store，不等同于所有 Codex 对话都保存在该 JSON 中。默认上限约 16MiB；实际风险取决于本地消息量。另在合成锁竞争中设置 250ms timeout，主线程零延迟定时器约 **292ms** 后才执行，验证了同步等待的阻塞性质。

压缩循环每删除一条又重新序列化全文件，批量淘汰时还存在额外放大；本次没有对极端淘汰规模给出性能结论。

整改：先移除 HTTP/事件路径上的同步等待，采用异步存储接口、按 session 分片、读缓存和原子写队列；再根据真实规模选择 SQLite/WAL。若采用 SQLite，同样避免把大查询同步放在事件循环里，并安排数据迁移、备份和回滚验证。

### F4：每次认证都改写状态文件

100 次并发 `verifyToken()` 在合成小文件中耗时约 28.5ms，同时产生 **100 次完整文件重写**。当前机器上单次成本不大，问题在于所有鉴权请求被写锁串行化，数据量和请求量增长后放大，同时扩大 B4 的竞争窗口。

多用户模式还有身份文件读取与 `touchUserSession` 更新；普通 API 请求会重复查询身份状态。

证据：`auth_store.ts:110`，`hybrid_auth_store.ts:154`，`server.ts:557`、`:710`。

整改：有效性校验保持可立即撤销；仅把展示用途的 `lastSeenAt` 合并到 30–60 秒写一次。使用 tokenHash 索引和有版本的状态快照。**不能通过长时间缓存“已认证”状态牺牲撤销实时性。**

### F5：首屏包接近预算，静态压缩仍按请求执行

| 指标 | 本次值 |
| --- | ---: |
| `app.js` 源文件 | 499,750 bytes，14,838 行 |
| `styles.css` | 112,311 bytes，5,579 行 |
| 已测 10 个 JS/CSS 资源合计 | 原始 705,148 bytes；gzip 142,833 bytes |
| 现有 critical budget 覆盖的 9 个资源 | gzip 142,374 / 143,360 bytes |

现有 build 是 TypeScript 编译，前端没有独立压缩/拆包流程；index 引入管理界面等脚本，service worker 也把这些纳入 critical cache。`app.js` 距源码预算仅剩 250 bytes，继续往同一文件增加功能很快会触发门禁。

服务端已经有版本缓存、ETag、gzip/Brotli，不能再把“缺少压缩和缓存”列为问题。剩余成本是每次生成 ETag、同步压缩；本机连续请求未缓存的 `app.js` Brotli 响应中位约 5.3ms，属次于 F1–F3 的优化。

证据：`public/index.html:26`、`service-worker.js:26`、`server.ts:1243`、`:7790`、`:7811`，`test/frontend_budget.test.ts:21`。

整改：按构建版本预生成原文/压缩体和 ETag；拆分管理、文件预览等低频模块，保留核心工作流优先加载；调整 service worker critical 清单。预算同时约束传输大小、解析/执行耗时，不应单纯提高上限。

### F6：文件预览与存储治理仍有增长成本

文件查看已具备单文件 64MiB、总读取 128MiB、并发 4 的保护，避免了完全无界读取。但浏览器会先把内容全部读成 text/blob，再创建预览；大 Markdown/HTML 又完整转换并渲染。文件下载也经过完整 buffer，未采用范围读取。

证据：`session_file_store.ts:64`、`:153`，`app.js:9890`，`server.ts:5492`。另外，报告读取前的 `maintainManagedStateStorage()` 会递归扫描多个管理目录，扫描与用户请求在同一链路，见 `server.ts:826`、`storage_governance.ts:134`、`:180`。

本项是代码确认的规模风险，未测真实大 PDF/大报告在手机上的崩溃阈值。

整改：区分“允许下载大小”和“允许预览大小”；大文本显示受限预览并允许下载，二进制下载使用有界流和必要的 Range 支持。清理采用后台定期任务/变化索引，容量校验仍保留写入时的硬边界。

## 7. 工程、测试与持续维护

### E1：沙箱测试把“浏览器尝试请求”误当成“网络请求成功发出”

现有用例监听 Playwright 的 `request` 事件，要求 HTML 预览完全不产生 `/html-probe.css`、`/html-probe.png` 记录。本次全量失败一次，单独复跑 3 次均失败。

进一步使用 CDP 和 route 拦截核实：两个资源都出现 `Network.loadingFailed`，`blockedReason: csp`；**没有 response，也没有进入 route 拦截回调**。前面的脚本不执行检查已通过；原用例在失败后未运行到刷新导航断言，该项应在修正后继续验证。此次证据支持 CSP 正常阻止资源加载，不能据此声称沙箱失效。

证据：`test/browser/workspace.spec.js:1074`、`:1104`。

整改：断言无服务端实际接收、无成功 response、脚本不执行、父页不导航，并核对 CSP blocked reason。保留安全目标，修正观测层级；不要通过削弱 CSP 来消除测试失败。

此外，fixture 的普通 session 路由主要提供完整详情，缺少生产主要路径 `/status` 和 `/timeline` 的等价实现，很多浏览器回归会落到兼容回退。应补 compact API 合约，避免 B2 这类新主路径没有真实浏览器覆盖。证据：`test/browser/fixture-server.mjs:305` 及路由分派。
