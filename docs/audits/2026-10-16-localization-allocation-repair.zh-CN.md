# 主浏览器崩溃调查与本地化重复切片修复

日期：2026-10-16。修复提交：`3dea3b9100f34f843b4588f548585382969cdede`，已合入远端 `main`。本次操作没有重启生产服务，合入分支不等于线上已部署。

## 已确认问题与证据边界

用户确认触发过程是“AI 正在输出，随后卡住并涨内存”。主浏览器 Crashpad 的两份转储时间为 09:26:54 和 09:27:00（Asia/Shanghai），进程注释的 origin 为 `https://aiops.orvibo.com`。崩溃后的三个页面目标读取堆指标超时；另一个可响应目标实际加载构建 `3bf9afca89fd7d7391eb`，通过 trace marker 映射到 renderer PID 75475。

可响应页面短时采样出现 `localizeFragment → localizeUiHtml → protectUiContentBlocks` 分配栈。该页面后续任务已结束，未复现多 GB 增长，不能替代崩溃标签增长前的保留链。最初工具连接到独立测试浏览器，发现后关闭测试标签并改用主浏览器已有调试接口；独立浏览器的结果不作为生产现场证据。

调查中曾把异常地址误读为约 4.7 GB 的单次申请，并错误描述为 SIGABRT；这些说法已撤回，不作为结论。转储中的 `page-allocator-mapped-size` 为 70,061,654,016 bytes（65.25 GiB），是虚拟映射指标，不能写成实际内存占用。未取得可归因到具体泄漏对象的符号化崩溃调用链或增长期堆保留链。

**本次确认并修复的是重复字符串处理缺陷，尚未证明它是用户多 GB 崩溃的全部或唯一根因。** 原始转储及采样保存在本机私有诊断目录，可能包含用户数据，不提交仓库。

## 缺陷、修复与容量

`public/ui-localization.js` 的 `protectUiContentBlocks` 原先每保护一段消息，就对剩余整段 HTML 执行切片和拼接。若有 K 个保护区间、输入长度 L，累计字符串工作可达 O(K×L)；当单段长度相近时，随消息数呈二次增长。缓存条数有界仍不能避免一次重绘产生的大量临时工作。

修复保持保护回调的逆序调用方式，从同一份原文按区间取片段，最后一次 `reverse().join('')`。受保护内容和区间间隙各切片一次，不截断消息、不改缓存上限。已排序保护区间的嵌套过滤改用递增结束边界，替代每个区间对其他区间的全量扫描；排序本身仍有 O(K log K) 成本。

同条件 Node VM 对照使用 80 段消息，精确统计 `String.prototype.slice` 返回值的字符总量：

| 指标 | 修复前 | 修复后 |
| --- | ---: | ---: |
| 输入字符数 | 740,085 | 740,085 |
| 累计切片字符数 | 29,998,220 | 740,085 |
| 输出字符数（保护标记形式） | 645 | 645 |
| 完整保留的保护块 | 80 | 80 |

累计切片字符量减少约 97.5%。这是工作量指标，不是分配字节、峰值内存或 GC 后留存量；V8 可共享字符串存储，不能把字符总量直接换算成实际内存。新回归要求累计切片量不超过输入的两倍，并验证内容与保护顺序；旧实现超过该上界。另有嵌套保护及相邻 UI 翻译回归。

曾尝试移除 HTML 本地化之后的 DOM 本地化遍历，随后撤回；该遍历的行为等价性未充分验证，不在最终修复中。后续优化必须保留翻译、任意字面占位符、嵌套内容和草稿行为，不能仅凭“看似重复”删除处理阶段。
