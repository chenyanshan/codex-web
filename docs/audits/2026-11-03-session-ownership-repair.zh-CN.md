# 会话重复归属修复

本次修复附件分析中确认的代码竞争，不声称还原了 2026-10-28 的生产请求顺序。
生产 `identity.json` 和应用 ID 引用未在本次代码提交中修改，也没有部署或重启生产服务。

## 实现与行为边界

- `FileIdentityStore.upsertSession()` 在现有跨实例文件锁内读取最新状态，检查 thread 唯一性，以及已有应用 ID 的 thread、owner、project 不可被普通更新覆盖。冲突抛出 `session_ownership_conflict`，HTTP 返回 409，不返回其他用户的映射。
- 历史导入使用独立 `importLegacySession()` 事务。已有 thread 的迟到补录直接跳过；重复导入、两个管理员并发导入均不会改写已有归属或归档状态。
- 将动态“无映射即历史”改为一次性、持久化的历史导入范围 `legacySessionImport`。在第一次管理员补录或第一次带归属的创建之前，从 **完整** runtime 目录记录候选 thread ID，绝不从 UI 分页或时间戳推测。所有参与者先完成范围初始化才能创建 thread；并发初始化只有第一次落库有效。
- 普通 POST、持久化提交（含 webhook）、定时任务的创建入口均执行上述步骤。恢复已有提交时也走唯一性检查。单用户、无归属任务仍沿用原来的单用户行为。
- 初始化读取失败时不创建底层 thread；后续请求可重试。数据库写失败或进程退出留下的新 thread 不在已固定的导入范围内，重启后不会被管理员误收。不会因延时到期或重启而扩大范围。
- 导入范围仅保存原始候选 ID；成功建立归属后移除候选，空范围仍持久保存。共享初始化 Promise 用 WeakMap 保存，并在成功/失败后释放。不在文件事务中等待 runtime 网络调用。
- 新映射的 `mappingAudit` 在同一事务中保存 source、actorUserId、correlationId 和真实 recordedAt。普通 HTTP 创建使用新应用 ID 关联本次请求，提交/恢复使用提交 ID，定时任务使用任务与 thread 组合 ID，导入使用本次操作 UUID。后续更新保留原始审计字段，不把 runtime 的历史时间冒充落库时间，不保存密码、令牌或提示词。

**明确的产品变化：** 首次迁移范围固定后，之后从其他 Codex 客户端创建的未映射会话不会再自动归给 admin。它们以及启用多用户前遗留但首次目录未返回的会话，需要单独核对归属后进行显式迁移；不得删除 `legacySessionImport` 来触发全量重新认领。这是消除“新建窗口被当作历史”的边界，不是延时去重。首次范围采集之前应停止旧版本写入者；不同版本进程同时写同一状态目录不在安全升级范围内。

## 存量数据核对与修复规则

新增只读工具：

```sh
node scripts/maintenance/audit-session-ownership.mjs /home/ubuntu/.codex-web
```

工具按 thread 分组，只输出必要归属字段；在状态目录 JSON/JSONL 内容和文件路径中检索应用 ID 的候选引用（包括分享、设置、收藏、提交、webhook 对话、阅读状态等实际保存的文件）。不输出文件内容、认证数据或提示词。大于 8 MiB、符号链接、非 JSON 内容明确列为未扫描，不能把这份候选清单当作完整迁移证明；浏览器本地草稿/缓存和目录外文件需另行核对。

生产修复需要在目标 Linux 主机进行以下独立操作。本次未执行：

1. 停止 `codex-web.service` 及其他可能修改同一状态目录的进程，确认备份空间足够；以仅管理员可读的权限备份完整 `~/.codex-web/`，以及有关的 `~/.codex/` 原始 thread/设置证据。将备份放在被扫描目录之外。
2. 在备份快照上运行只读工具并保存报告，确认每个重复组的原始创建记录、提交回执、认证主体与 mapping 来源。旧记录没有 `mappingAudit` 时，不补造来源。
3. 针对每个 thread 写明保留的应用 ID、归属证据、被替代的应用 ID 和逐个引用的处理方式。不能默认非 `app_legacy_` 的 ID 就可靠。附件中的 AIOps 组仍需按现场引用核对，不能仅凭附件删除记录。
4. 按最终确认的账号保留唯一映射。收藏/设置冲突保留双份证据再明确选择；提交回执不能改动原 owner、提交 ID 或执行状态，更不能触发重新执行；分享 capability 涉及原归属，默认撤销后由合法 owner 重建，不把跨账号链接静默迁移；附件、阅读状态、webhook 对话也需逐项校验。发现不能无损或合法合并的引用时保留备份、暂停该组迁移。
5. 仅在停机快照上原子写入经审核的数据变更，绝不删除底层 Codex thread。再次生成差异与重复组报告，测试原用户读取、其他普通用户拒绝访问、归档/收藏/提交回执/分享撤销，再启动新版本服务。保留备份用于整组恢复，不能只恢复 `identity.json` 而遗漏关联文件。

代码不会自动猜测或删除已有重复记录。现存重复归属的访问和引用问题，需要以上数据修复完成后才能宣告解决；新唯一性检查会阻止继续更新冲突映射。

## 回归与优化保留

确定性测试用 Promise 屏障安排交错，不依赖随机延时：正常先写与旧快照晚补录、补录先写后的跨账号冲突、两个管理员并发导入、重复导入、完整历史仍能导入、跨实例范围竞争、失败重试、重启不重新认领、新映射审计字段不可被更新伪造。HTTP 屏障覆盖直接创建和持久化提交，检查 admin/bob 不可写 alice 的新会话；定时任务也覆盖底层 thread 可见窗口。已有 webhook、恢复、鉴权、分享、归档等接口测试继续保留。

受影响优化：

- OPT-05：提交 ID、回执与恢复语义保留；ownership 冲突不转为重复创建或跨账号成功。
- OPT-19：使用原 FileVersionCache 及事务写入失效；首次迁移必须读完整目录，之后保持分页接口。
- OPT-20：新增迁移范围是有限历史候选且只减不增；初始化 Promise 在结束时释放，排查单文件临时读取上限 8 MiB。
- OPT-21：正常用户归属检查和分享权限不放宽；跨 owner 冲突不返回别人的记录。

其他 OPT 项没有修改对应实现。本次没有前端加载/SSE/渲染改动；同步最新 main 后仍执行前端预算检查，140 KiB 上限不变。真实生产存量迁移、设备检查与长期内存测量未执行，不据此宣称生产数据已修复或浏览器长期稳定。

验证结果：类型检查通过；以下测试共 262 项通过，包含生产首屏预算检查。还曾临时恢复修复前的 `server.ts`（其余存储防线保留）运行两个 HTTP 屏障回归，二者均在“新 thread 被 admin 补录”的断言上失败；恢复修复版后二者通过。这验证了存储唯一性检查本身不足以关闭创建窗口。
