# Runtime and storage remediation

This note describes implementation and synthetic regression coverage; it does not alter the original audit or claim production/iOS measurements.

## Directory and history

`SessionDirectory` loads one provider page for a cold unfiltered list and walks remaining pages in the background. Empty pages with cursors are supported; cursor cycles and provider failures remain errors. Concurrent full-catalog readers share completion. Search and state filters await complete catalogs. The HTTP contract marks incomplete lists as indexing and withholds normal pagination until the client reloads the completed first page. Locally observed running, approval and failure sessions are merged independently of directory position; activity outside this process becomes known as background pages arrive.

Stable directory arrays reuse runtime summaries and the list paginator's sorted index; cursor lookup uses binary search. Scope and principal cursor checks remain in place. Directory snapshots refresh after 30 seconds and mutations invalidate them. A failed refresh is retried by the next reader. Compatibility lookup walks active and archived catalogs, shares concurrent scans and never converts a provider failure into an absent thread. A provider lacking turn-history support yields an explicit `history_unavailable` error from the timeline API while its session metadata remains accessible.

`readSessionMetadata` supplies cwd and summary without requesting turns. `readSessionTimeline` builds a history projection once and reuses it until thread metadata, a turn lifecycle event, or the per-session local store revision changes. Token deltas keep the stable history projection; active output arrives through SSE. The provider still requires an initial full-history read. Warm pages do not reparse that history. Metadata refresh has a five-second cache, so externally changed history can take up to that interval to invalidate. The cache is bounded to 32 sessions and 64 MiB of serialized thread/timeline data; a single projection over that budget is not retained. HTTP presentation slices the page before DTO mapping. Business timestamps exclude transport heartbeats; failure/stale attention preserves approval and active priority.

## Persistence and recovery

Session settings and supplemental timelines now use async filesystem and async cross-process locks. Session shards are immutable and the atomic `manifest.json` rename is the commit point. Mutations reread the manifest under the lock; timeline upserts are one transaction. Reads cache up to 64 shards / 16 MiB and detect manifest replacement. A reader racing shard retirement retries the current manifest. Settings snapshots are reused until their manifest revision changes, avoiding a full settings scan on each status call.

On first access, valid legacy v1 JSON is copied to `<path>.migration-backup`, normalized into `<path>.d/` shards and committed as a v2 manifest. The legacy source remains untouched. A committed partition is never remigrated from stale legacy data. Invalid source/manifest/shards fail closed rather than overwriting accepted data.

Each commit retains its preceding manifest as `manifest.backup.json` and keeps its referenced shards. Older shard versions are normally retired immediately; background housekeeping removes interrupted-write orphans and retries failed retirement. A retirement error after the manifest commit does not report the accepted mutation as failed; extra orphan bytes can remain until cleanup succeeds. The live timeline byte budget remains enforced on writes; the recovery snapshot can consume one additional live budget, with one additional in-flight shard during commit. Backups are intentional additional disk use, not part of the live-data quota. Compaction uses a bounded binary search within the changed session and evicts the largest other partitions only when the global live-data budget requires it; this is a size policy, not a recency policy.

To recover corruption, stop the service and preserve a copy of the entire `<path>.d` directory first. Validate the backup manifest and all referenced shard JSON; copy `manifest.backup.json` to a temporary file and atomically rename it over `manifest.json`. Restart and verify the recovered state. This restores the preceding commit and can discard the latest write; recovery is deliberately explicit. The migration backup is a pre-migration rollback point only: restore it to the legacy path and move the partition directory aside while the service is stopped. Never treat that old backup as a current-state backup after subsequent writes.

Read routes schedule coalesced background managed-storage maintenance. Capacity-enforced writes still scan authoritatively under the shared async lock, preserving hard quotas even if another process wrote files. Thus write cost can still scale with managed file count; it no longer sits on ordinary read responses. Aggregate diagnostics count directory provider pages, projection hits/builds, and storage scans/files without logging content.

## Verification

Focused regression suite covers compatibility page/empty-page/archive/cycle/provider-error cases, request coalescing, 1000-thread cold/background directory costs, history reuse/invalidation, cross-process settings/timeline writes, migration/restart, deliberate recovery, bounded retained shard versions, hard quotas and 1000 actual saved settings. At the recorded run, 108 focused tests and repository typecheck passed. The 1000-thread cold call performs one provider request; full completion performs ten. Warm status reads reuse one settings snapshot until its revision changes. See test diagnostics for machine-specific timings rather than treating them as production percentiles.
