# 轻量随身 Codex Web：官方能力复用实施计划

日期：2026-09-29。更新：2026-09-30，S0—S5 已在工作区实现，最终验收见[集成记录](../../audits/2026-09-30-portable-codex-integration.zh-CN.md)。尚未升级宿主机 CLI 或部署；以下为原实施范围和验收要求。

依据：[代码对照报告](../../audits/2026-09-29-portable-codex-capability-review.zh-CN.md)、[21 项保留基线](../../architecture/2026-09-25-existing-optimizations-baseline.zh-CN.md)、当前工作区源码和官方提交 `68e1a421f55ec8a0e900c5a250aa83c13727b671`。实施时选用已核实的发布版源码；main 仅作为参考，不能代替本机版本验收。

## 1. 交付目标与范围

手机随时能看懂 Codex 在做什么、回答问题、停止或追加指令、查看结果，并知道运行时是否已更新。保持现有视觉风格和 HTTP/SSE 架构，不做 IDE、终端工作台、插件商城或多代理调度平台。

完整计划覆盖九组能力：重试健康、结构化问答、计划、子代理活动、压缩状态、上下文用量、本轮 diff、工具活动、app-server 更新。分阶段交付；会话分叉、专门 review 入口、手动压缩不纳入本轮。

页面新增面限为：状态行、折叠活动面板、问题卡、按需改动详情、设置中的运行时条目。复用现有弹层、文件预览、审批风格；不引入前端框架、状态管理依赖、独立消息通道、第二套任务队列或第二个持久化数据库。

用户已明确否定当前折叠面板的视觉效果。第一批增加[活动面板视觉与交互改造](2026-09-29-portable-codex-activity-panel.md)：先整理当前摘要/列表/详情的层次并做浏览器原型验证，再接更多能力；不得直接把新功能堆入现有四列列表和多行摘要。

## 2. 如何“尽可能直接照搬官方”

| 内容 | 复用方式 | 不做的事 |
| --- | --- | --- |
| 运行、重试、工具、子代理、压缩 | 继续直接使用官方 app-server 执行 | 不复制 Rust 引擎进本项目，不再实现模型请求重试 |
| 协议字段 | 使用目标 CLI 生成类型，记录来源和差异 | 不凭 main 手写目标发布版不存在的字段 |
| UI 状态分流 | 按官方 TUI 的 notification/item 分流和恢复语义移植为小型 TS/JS reducer | 不逐行搬终端绘制、焦点、布局和桌面专用状态 |
| 重试提示 | 复用 error/willRetry、错误详情、官方重试文案 | 不按日志文本猜次数，不由 Web 层自动重发 turn |
| 问答 | 复用官方问题/答案 schema、isBlocking 和请求生命周期 | 不将“回答问题”改写成一条普通聊天 steer |
| 更新 | 复用官方分发、安装来源识别原则和现有兼容脚本 | 不为项目分叉一套 Codex 发布渠道，不迁移 daemon 架构 |
| 测试 | 将官方相关用例的输入和行为断言转成项目 fixture | 不复制整个上游测试框架 |

建立轻量复用清单，记录上游 commit/文件/符号、本地映射、必要改动、对应测试。直接复制或改写具有实质表达的代码时保留 Apache-2.0 来源及适用 NOTICE；现有 generated/LICENSE 不能自动覆盖所有新增文件的来源说明。

首选官方参考：`tui/src/chatwidget/protocol.rs`、`streaming.rs`、`compaction.rs`、`tool_lifecycle.rs`、`turn_runtime.rs`；执行规则参考 `core/src/responses_retry.rs`，更新参考 `tui/src/update_action.rs`。不得把“官方有重试”解释成“Web 应自己再重试一次”。

## 3. S0：固定集成基线与协议契约

步骤：

1. 先确认同时进行的 canonical timeline 改造的集成边界，记录工作区 revision/差异和实际运行 dist；不覆盖他人修改、不顺手部署当前未完成工作。
2. 记录正在运行的 app-server 版本/进程身份、磁盘 CLI 版本/实际路径、协议生成版本。不能用新执行的 `codex --version` 冒充运行中进程版本。
3. 检查选定发布版的通知、ServerRequest、isBlocking、request resolution、子代理字段和 snapshot 能力。生成类型含 EXPERIMENTAL 注释的条目单独标记。
4. 用 `scripts/app-server/compatibility.ts` 建立可复用能力清单。只对明确不支持降级，不能吞掉授权失败、超时或上游异常。
5. 记录基线测试结果；已有失败单独归因，不弱化断言。

产物：来源与能力表、协议 fixture、受影响文件清单。不得为发现能力而在真实用户会话中执行任务或修改配置。

完成条件：能明确每项能力在目标运行时是可用、实验、不可用或未验证，且源码/部署状态不混淆。

## 4. S1：重试可见和统一活动投影（第一交付）

建议新增 `codex-native-api/src/app_server/activity.ts`、`codex-web/src/turn_activity.ts`、`public/turn-activity.js`；名称可依当前模块调整，禁止借机整体重写 runtime/app.js。

步骤：

1. 在现有官方通知路径解析重试、终态、plan、ContextCompaction、工具和协作条目。保留 threadId/turnId/itemId 身份；错误详情做长度限制与脱敏。
2. 第一批只上线重试、压缩和最近实际活动时间。计划/子代理/工具字段留明确扩展点，不一次实现全部 UI。
3. 生命周期仍由官方终态决定；另建有界活动快照表达观察连接、重试、当前活动。不要引入第二个任务终态来源。
4. 状态改变才发布；复用 SSE epoch/sequence/reset。快照随现有会话详情返回，旧快照不能覆盖新事件，旧 turn 不覆盖新 turn。临时活动状态不写成 canonical 聊天消息，也不更改聊天排序。
5. 对同轮重复错误合并为最近错误与计数；计数只表示本服务观测到的次数，不冒充官方尝试次数。官方提供次数时才原样展示。
6. 收到实际输出/工具进展后按语义恢复状态；心跳、轮询成功和无关元数据不算进展。终态不能被迟到的重试覆盖。
7. 无进展提示先使用固定保守阈值，不建策略后台：3 分钟提示“未收到新进展”，10 分钟加强提示并进行一次受现有节流约束的校准。等待审批/问答/子代理/长命令时显示已知原因；不自动终止，不重发任务。

弱网约束：缓存可显示最后观测状态，但离线/身份待确认时标记未校准，不把旧“工作中”当实时状态；服务重启无法恢复的重试信息显示未知。前端离线计时不是后端进展证据。

有界策略：复用现有会话和事件容量预算，活动详情额外设小上限；建议初值每轮最近 20 条摘要、单字段最多 2 KiB、快照最多 32 KiB，最终按实际 fixture 校准。被截断时提示详情不完整，不无限堆积历史事件。

完成条件：浏览器能区分重试、观察断线、正常活动和最终失败；刷新/断流后能校准；没有额外每秒轮询，没有重试风暴。对照官方重连恢复用例验证。

## 5. S2：结构化问答（第二交付）

建议 `app_server/user_input.ts` 管请求映射，Web 复用现有授权及有界持久化设施，前端增加问题卡模块。先接 item/tool/requestUserInput；MCP elicitation 涉及另一类 schema/授权，本轮保持明确不支持，不假装已接入。

步骤：

1. 从现有 `handleServerRequest` 分离出问答分支，其他未知请求仍明确拒绝，禁止自动作答或自动批准。
2. 请求身份绑定 connectionIdentity/epoch、thread、turn、RPC ID；isBlocking 决定是否显示等待回答，不能从文案推断。
3. 新增会话所属的答复与答复状态查询接口；沿用当前角色/项目授权，分享页面不暴露交互或敏感问题。多个浏览器竞争回答只接受一个确定答案。
4. 浏览器生成 answerSubmissionId，服务端以该身份记录有限回执。复用现有回执设计原则和存储设施，但问答状态与 start/steer 回执类型明确区分。
5. 必须先持久化“准备发送/结果待确认”，再尝试发送 RPC 响应。HTTP 响应丢失时查询原回执，不自动再向 app-server 写一遍。
6. JSON-RPC response 不一定有接收确认：区分本服务已收到答案、已尝试交付、官方已解决、结果未知。只有匹配的官方 resolved/可靠后续状态才支持更强确认；不把 socket.send 成功宣称为模型已收到。
7. 如果进程在发送边界崩溃或连接 epoch 改变，旧 RPC 不可盲目重放。对账后标记过期/未知；允许用户复制答案继续处理，不自动执行新 turn。
8. 回答草稿按用户/会话/问题保存；离线先保存文字，重连核对问题仍有效后才能提交。不得用过期倒计时自动提交默认选项。

完成条件：选择项与自由文本可答；阻塞/非阻塞都正确；刷新、双设备、POST 丢响应、连接重建、请求已解决、存储失败均不会重复回答或误报成功。

## 6. S3：计划、子代理、工具详情（第三交付）

在 S1 同一活动投影上补齐，不再建实时通道。

1. 计划消费 turn/plan/updated，在折叠面板中展示原始步骤状态；无官方步骤时不生成百分比。
2. 子代理消费官方协作条目和 agents_states，显示状态与最后观测时间。先不全量订阅子线程，也不开放任意子代理控制。
3. 若上游只提供启动时快照，明确标“最近观测”，不能冒充实时。按需展开的子线程读取必须验证归属、限并发、切会话释放，未通过授权证据则只显示摘要。
4. MCP/搜索/图片生成等条目复用同一活动卡；详情按需加载，保留现有命令/文件批次兼容。
5. 终态、取消、子代理失败都有明确展示；父任务成功不隐去已知子任务失败，子代理运行也不自动清除父任务重试。

完成条件：能解释“父代理没输出但子代理在做事”；活动展开不抢输入焦点、不打断旧消息阅读，不增加后台全量拉取。

## 7. S4：app-server 版本与更新（核心维护能力）

可在 S1 稳定后实施，不要求等 S2/S3 全部完成。只做设置中的单一运行时入口。

### S4a：先实现版本可见和应用已安装更新

1. 明确区分 Web build、磁盘 CLI、运行中 app-server、协议验收版本；获取不到运行版时显示未知，不能用磁盘版替代。
2. 运行时状态接口只读并缓存，不让每次页面渲染执行 CLI 子进程；详情仅向有权限的用户展示，更新操作仅管理员/单用户所有者可用。
3. `/api/runtime/reload` 保持 MCP reload 语义，UI 清晰命名，不复用它承载升级。
4. 提供“空闲后应用已安装版本”和取消预约。预约保存在现有状态目录的小型原子状态文件，最多一个维护任务，不引入通用调度服务。
5. 切换前统一暂停 start/steer/goal 自动续跑/定时任务/Webhook 新执行入口；与最终全局空闲检查在同一维护锁下协调，避免先查空闲后进入新任务的竞态。审批和问题答复在排空期间仍可用于完成旧任务。
6. 活动判断包含父子线程、后台任务、待审批/待回答；无法确认全局空闲时等待，不杀进程。页面显示等待原因，允许取消。
7. 空闲后仅重启所拥有的 app-server，并重新 initialize、刷新模型/配置/能力缓存、触发订阅 reset 和会话校准；若当前架构必须重启 Web，明确展示维护断连并复用现有服务脚本。
8. 更新不产生隐式聊天重发；outbox 恢复先查回执，旧 RPC 失效，草稿与已确认消息保留。

### S4b：再实现受支持安装方式的一键更新

1. 按真实安装来源选择官方更新方式。优先支持当前宿主机实际使用的方式，未知安装来源显示手动更新说明，不扫描或接管所有全局安装。
2. 固定目标稳定版本并记录来源，操作期间不反复解析 latest；不能声称 latest 自动兼容。
3. 下载/准备阶段尽量不影响旧进程。具备安全并存安装条件时，先对候选二进制运行已有隔离兼容检查，再安排切换。原地包管理器升级无法保证旧安装可恢复时，应明确限制，不能伪称原子升级。
4. 更新由独立于 HTTP 请求生命周期的受控维护任务执行，管理员刷新或手机断线不重复启动安装；查询同一 operation ID 的有限状态和结果。
5. 切换按 S4a 的排空、锁和校准机制；没有运行中任务热迁移。安装失败/初始化失败保存错误摘要，尝试可验证的旧二进制恢复。
6. 保留旧二进制和配置不等于保证数据回退。新版可能迁移运行状态；只在确认状态兼容的条件下自动回退，否则停止切换并提供恢复信息，不盲目恢复旧状态覆盖新数据。

完成条件：安装成功/待生效/实际运行新版本三者可区分；断网刷新不重复更新；活跃任务不被默认打断；更新失败可定位且不会误报成功。

## 8. S5：上下文用量与改动详情（收尾）

1. 接 thread/tokenUsage/updated，保留 total/last/modelContextWindow 含义。累计消耗不当作当前上下文占用，更不按 token 自行推算费用；provider 不给数据则显示不可用。
2. 接 turn/diff/updated，复用文件预览与折叠详情。大 diff 按需获取并设上限；流上只传必要摘要，不能每次增量重传完整大 diff。
3. 已授权会话才可读 diff；对分享和观察角色按既有可见范围过滤，缓存键带身份/会话。测试 diff 缺失与截断提示。

完成条件：默认对话不增加明显视觉密度或启动请求数，展开详情才产生必要加载。

## 9. 弱网与轻量硬约束

- 继续 HTTP + SSE，一个会话主事件流；健康/计划/工具不各自建立轮询器。
- 保留 existing epoch/sequence/reset、canonical message generation/revision 的各自语义；活动快照不能代替消息 checkpoint，也不另造一套聊天排序。
- 网络状态与任务状态分开。超时代表结果可能未知；不自动重新 start、steer、答复或更新。
- 缓存先可读，后台校准；新请求不能清空已有内容。缓存不完整要标识，不声称离线实时状态。
- 重试采用现有退避和随机抖动；连接恢复合并触发，避免 focus/online/pageshow 同时全量刷新。
- 前后台切换保存草稿/答复草稿/阅读位置；新状态只局部渲染，不滚动抢焦点。
- 日志只记有界、脱敏的错误及状态变化，重复错误合并；不增加每秒完整快照日志。
- 新前端模块加入现有静态资源、版本散列、Service Worker 和构建清单；复用完整缓存保护，不让半更新脚本破坏离线页面。
- 前端使用项目 frontend-design 技能并保留当前风格。新增状态不靠颜色单独表达，手机窄屏可读。

## 10. 验收与发布门槛

每阶段各自完成 focused tests 和 `npm run typecheck`。UI 阶段运行相关浏览器 fixture，并实际查看手机/桌面截图；协议阶段对目标 CLI 做真实 app-server 冒烟，区分不消耗推理额度的检查和真实模型调用。测试通过不能冒充已经上线。

必要场景：

| 场景 | 必须满足 |
| --- | --- |
| 524/429/断流后重试成功或失败 | 及时提示；结果正确；不重复 turn |
| 无输出长命令、压缩、父线程等待子代理 | 不误判终态；等待原因准确或明确未知 |
| SSE 静默、断点过期、后台恢复、整页刷新 | 快照校准；旧状态不覆盖新状态；缓存仍可读 |
| 问答 POST 已接收但响应丢失、双设备回答 | 原身份查询；单次答复；不把未知说成功 |
| 问题过期、RPC epoch 变化、服务重启 | 不重放旧 RPC；保留草稿并明确过期 |
| 更新中刷新/断网、安装失败、启动失败 | 单维护任务；可查状态；不误切新版本 |
| 更新排空时 Webhook/定时任务/目标继续到达 | 统一闸门；不抢占既有任务；恢复后无重复执行 |
| 换账号、撤权、分享、子线程与 diff | 先授权再读取；旧缓存不得绕过权限 |
| 高频工具输出、大 diff、长会话 | 内存、日志、流量有界；阅读位置不变 |

性能验收以同一设备/fixture 的前后对照为准：默认不增加独立后台轮询；启动依赖预算测试继续通过；重复状态不产生持续新事件；大 diff 不进入每秒推送。没有对照数据不宣称性能提升。

OPT 对应：S1/S3/S5 重点 01/02/03/07/08/09/10/11/12/13/16/17/19/20/21；S2 加 04/05/06；S4 重点 01/02/04/05/07/15/19/20/21。14 附件与 18 静态传输实现保留并跑受影响回归；所有新增前端资源验证 15/18。逐阶段在审计记录写明通过、未验证、未受影响及回退方式。

实现按阶段提交，不依靠删功能或弱化断言通过测试。集成后再准备实际部署清单；更新/重启影响运行任务时按本计划排空，不能用当前诊断会话还活跃的进程做强制更新验收。

## 11. 控制范围与停止条件

首个可交付版本是 S0 + S1 + S4a，先解决看不见异常和版本不明；第二批 S2 + S3；第三批 S4b + S5。S4b 必须完成，若安装方式不支持受控更新，应明确为该宿主机未交付，而不是把手动说明冒充一键更新。

第一批同时完成活动面板 V0/V1，S1 新状态沿用该布局；第二批执行 V2，相关阶段均须通过 V3 视觉与弱网验证。面板改造以复用现有模块为主，不另建大型组件系统。

任何阶段若需要新数据库、通用任务平台、完整终端、全量子代理常驻订阅或重写 app.js，应先缩减实现并记录原因。保留必要的状态正确性不能被“轻量”删掉。

不设未经验证的精确工期。主要不确定性是目标 CLI 的问答重连语义和安装方式的切换/回退能力；S0 必须先验证这两项，再给工作量估算。
