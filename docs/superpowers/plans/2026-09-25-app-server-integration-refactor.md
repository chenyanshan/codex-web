## 1. 交付目标与范围

将当前已经使用 app-server 的集成层，逐步改造成职责清晰的官方协议薄客户端。用户仍通过更新 Codex CLI 追新；项目减少对内部会话文件、stderr 文本和实验性原始事件的依赖，并能重复验证升级兼容性。

前端必须使用项目安装的 [frontend-design](../../../.agents/skills/frontend-design/SKILL.md)。**用户认可当前风格，保留现有视觉语言是明确要求，同时允许有依据的前端优化。** 在现有主题和布局体系内改善信息层级、可读性、操作效率和性能；保留现有弱网及其他优化机制，不能为了精简代码而损失用户能力。

本轮实施范围：官方协议接入、任务状态、历史恢复、Web 对接、必要前端适配、版本兼容验证、部署验收。保持现有功能、HTTP/SSE 接口、单用户及可信团队模式。

会话分支、服务端队列、交互终端和文件浏览器属于后续功能包，不作为本次底座改造完成条件，也不与核心迁移同时上线。

## 2. 实施顺序

| 步骤 | 对应设计阶段 | 交付物 | 通过后可以做什么 |
| --- | --- | --- | --- |
| S0 基线盘点 | P0 | 协议映射、补丁台账、行为与视觉基线 | 明确可替换和必须保留的实现 |
| S1 兼容测试 | P0 / P4 前置 | 可重放协议 fixture、隔离集成测试入口 | 开始替换内部实现 |
| S2 薄客户端 | P1 | 官方类型、连接管理、能力边界、旧 facade | 将调用端逐项迁移到类型化接口 |
| S3 状态与历史 | P2 | 官方事件驱动与恢复逻辑、收敛后的兼容补丁 | Web 使用统一的执行状态来源 |
| S4 Web 与前端 | P3 | 保持风格的状态/审批/恢复交互、产品回归 | 验证真实端到端体验 |
| S5 追新验证 | P4 | 版本验证命令、版本诊断、升级与回退手册 | 重复评估后续新版 CLI |
| S6 部署验收 | 发布 | 验证记录、切换与观察结果 | 关闭改造任务并进入常规维护 |

顺序为 S0 → S1 → S2 → S3 → S4 → S5 → S6。前端设计基线在 S0 建立，S1 的测试随每步改动持续补充；S5 是整理和自动化已有验证，不是最后才测试。

每一步按独立变更集交付，记录改动、验证结果、剩余兼容项和回退方式。前一步未满足退出条件时先解决问题，避免把风险累积到最终切换。

## 5. S2：建立官方协议薄客户端

在现有 `codex-native-api` 包内增量拆分，保留 `CodexAppClient` 导出作为过渡入口。建议新建 `src/app_server/` 下的 `generated/`、`transport.ts`、`client.ts`、`capabilities.ts` 和 `compat/`；最终文件按职责控制大小，不复制一套并行客户端。

- [x] 使用目标 CLI 的生成器生成类型，保留必要的来源/许可说明，并记录版本、命令和生成结果摘要。
- [x] 将官方 wire 类型与 `Provider*` / Web 展示类型分开；减少手写协议字段，但不强迫上游类型泄漏到浏览器。
- [x] 从现有实现提取初始化、请求关联、超时、通知、服务端请求、关闭和子进程生命周期处理。
- [x] 维持当前 loopback WebSocket 接入；连接失效时清理悬挂请求，防止重复启动或遗留自己拥有的 app-server 子进程。
- [x] 对关键消息做运行时结构检查；未知可选字段不导致整条会话崩溃，未知审批请求不能自动接受或静默丢弃。
- [x] 将实验依赖集中登记，只为实际需要的功能启用；不直接关闭全局实验开关而破坏已有功能。
- [x] 根据目标版本实际存在的发现机制或已验证能力表处理可选接口；只有明确的“不支持”才降级，认证失败与超时正常报错。
- [x] 逐项迁移现有模型、配置、Skills、插件、MCP 等调用，保持公开导出和其他包入口兼容。

**验收：** 现有调用端无需整体重写；官方协议字段有类型约束；连接和错误路径测试通过。没有在启动时重新生成源码，也没有引入新的 app-server 安装渠道。

## 6. S3：收敛任务状态和历史恢复

主要涉及 `CodexAppClient.waitForTurnResult` 及其辅助函数、Web `runtime.ts`、设置/时间线 store 和订阅逻辑。

- [x] 以官方 thread/turn/item 身份关联结果，保留当前 Web session 映射。
- [x] 将成功、失败、中断和审批状态交给目标协议驱动；观测断线单独表示为待同步，不伪造执行终态。
- [x] 正常连接以事件为主；首次加载、恢复和必要的受控校准读取官方状态，限制轮询频率、并发和重试次数。
- [x] 验证早期事件缓冲、历史与订阅交接、去重与顺序；不能按相同文本粗暴去重。
- [x] 保留 Web 提交幂等与查询回执；结果不确定时先校准，无法确认就明确保留不确定状态。
- [x] 先验证官方错误与终态接口能覆盖旧故障，再逐项撤下 stderr 和内部会话文件的任务判断路径。
- [x] 未能替代的补丁集中到 `compat/`，标明影响版本、测试和删除条件；进程启动/崩溃诊断仍可使用 stderr。
- [x] 多用户、多任务共享进程时，错误必须正确关联，不把全进程输出误归给单个 turn。
- [x] 需要旧新路径比较时，对同一份事件做只读投影比较；不为对照启动两份真实任务。

**验收：** S1 的故障与恢复用例通过；主路径不再依赖内部磁盘格式猜测结果，保留例外有明确证据。Web 缓存不能覆盖更新的官方状态，正常历史与已有附件不丢失。

## 7. S4：Web 对接与前端适配

后端重点：`runtime.ts`、`event_model.ts`、`event_bus.ts`、`server.ts`。前端重点：`app.js`、`network-recovery.js`、`submission-delivery.js`、`timeline-reconciliation.js`、`session-attention.js`、`work-details-view.js`、`ui-copy.js`、`ui-localization.js` 和 `styles.css`。

### 7.1 先写设计说明，再实现

每次前端改动先按 `frontend-design` 写简短设计说明：改动影响哪个现有位置、复用哪些 token/组件、用户会看到什么状态和操作，以及具体解决什么可用性问题。随后对照用户“当前风格挺不错”的要求自查，完成实现后截图复核。优化可以超出新增状态提示，但须保持原有风格并给出可验证的收益。

技能明确要求以用户 brief 为先；它关于避免通用模板、选择鲜明视觉方向的建议，不构成替换现有主题、字体或布局的理由。

当前代码可确认的基础如下，实施时再与截图基线核对：

| 设计项 | 延续方式 |
| --- | --- |
| 颜色 | 使用现有语义变量，不在组件内新增一套硬编码色板 |
| 默认主题示例 | `fresh-light`：背景 `#f4f5f7`、侧栏 `#eaecef`、卡片 `#ffffff`、正文 `#1f2937`、次要文字 `#6b7280`、强调色 `#10b981` |
| 用户主题 | 保留保存的主题；兼容 `retro`、`dark-gold`、`oled-black`、`fresh-light`、`terminal`，不强制改成默认主题 |
| 字体 | 沿用系统无衬线字体及中文回退；代码区使用原有等宽字体，不引入展示字体 |
| 布局 | 延续桌面项目/会话/聊天分栏和手机单会话/抽屉；保留现有 `current` / `console` 布局选择 |
| 层级 | 延续消息、命令详情、审批和输入区的现有组件层级、密度、间距与圆角 |
| 动效与可用性 | 只在状态变化需要时反馈，保持可见焦点、触摸目标、对比度和 reduced-motion 行为 |

布局意图为在现有位置完善反馈，不增加一个新的工作台：

```text
桌面： [项目栏] [会话列表] [会话标题与状态]
                          [消息 / 工作详情 / 审批]
                          [输入区与发送回执]

手机： [返回 / 会话标题 / 状态]
       [消息 / 工作详情 / 审批]
       [输入区与发送回执]
```

普通聊天只呈现用户需要采取行动的信息，例如“正在恢复连接”“正在确认是否发送成功”。版本、协议和兼容诊断放在已有管理员设置/诊断区域；共享用户界面不暴露二进制路径或其他宿主机详情。

### 7.2 实施任务

- [x] 对齐官方事件与现有 Web 事件，保持 HTTP/SSE 核心契约；确需新增字段时采用向后兼容扩展并验证旧缓存。
- [x] 保留 SSE epoch/reset、重放边界、缓存上限、慢客户端处理及持续鉴权。
- [x] 复用现有连接状态和提交回执组件，明确区分“未发送”“等待确认”“执行中”“等待审批”“已完成/失败/中断”。
- [x] 历史恢复不重复插入消息，不抢滚动位置，不清空草稿和附件；切换会话时不串消息或沿用过期状态。
- [x] 审批卡片保持原风格，决策处理中避免重复点击；断线或审批已失效时给出明确反馈。
- [x] 保持前端英文/简体中文文案一致，延续主题与布局偏好，不增加与任务无关的技术标签。
- [x] 保持附件、文件路径限制、分享能力、Webhook 和用户/项目权限，不因改接官方接口绕过现有检查。
- [x] 涉及静态资源变更时使用现有构建与 Service Worker 更新机制，验证缓存更新和重新连接。

### 7.4 必须保留的机制与可进一步优化的项目

以下“现有基础”依据代码与测试用例盘点，本轮重跑结果与限制已记录在验收文档的 OPT 对照表。允许替换内部实现，但必须保留其对用户的效果、失败处理和访问边界。

完整保留项、措辞边界和测试入口以 [21 项保留基线](../../architecture/2026-09-25-existing-optimizations-baseline.zh-CN.md) 为准；下表的可优化方向不构成削减现有能力的理由。

| 领域 | 现有基础与必须保留的效果 | 可进一步优化的方向 |
| --- | --- | --- |
| 弱网恢复 | 请求超时/取消、SSE 退避与抖动、游标恢复、前台与联网恢复；连接断开不等同于任务失败 | 统一恢复状态，合并同一范围的重复恢复请求，避免多处提示冲突 |
| 本地会话缓存 | 会话摘要、最近 5 个会话的有界对话缓存；可用内容先展示，再校准 | 缓存新旧状态更清楚；恢复失败保留已有内容，不闪白 |
| 消息送达 | 待发送纯文本/乐观消息持久化、提交 ID、查询回执；结果未知不盲目重发 | 清楚区分待发送、确认中和已送达，收敛手动重试入口 |
| 草稿与附件 | 按身份/会话保存草稿和已上传附件引用；上传进度、逐文件重试/取消、并发控制 | 存储失败反馈、长输入和附件较多时的操作效率；不承诺未上传文件刷新后可恢复 |
| 长会话阅读 | 历史分页/窗口、滚动锚点、用户阅读优先、更新期间不强制拉到底部 | 历史入口、回到最新和新消息提醒更明确，保留现有重新打开会话时的定位行为 |
| 加载与渲染 | 模型慢请求不阻塞主界面、会话内容分步显示、局部 DOM 更新及持久化防抖 | 先测流式输出重绘、长任务和布局抖动，再做增量更新与调度优化 |
| 多会话与竞态 | 请求代次/身份检查、迟到结果隔离、多设备与前后台状态校准 | 进一步检查快速切换、标签页恢复和异常请求下的稳定性 |
| 附件与预览 | 图片/文件/Markdown 等预览、取消旧请求、资源释放、下载与文件权限 | 按需要优化加载占位、错误入口及大内容渲染，不破坏选择、复制和下载 |
| PWA 与资源更新 | 版本化静态缓存、离线应用壳、更新不完整时保留旧完整资源 | 更新提示和恢复流程更一致，不在编辑中强制刷新 |
| 移动与桌面布局 | 分栏与抽屉、布局模式、主题、字号、语言、横竖屏及调整尺寸行为 | 输入区、按钮触达、审批布局、长文和代码可读性 |
| 服务端性能 | 静态资源压缩/ETag、事件字节与数量上限、SSE 慢客户端处理、存储配额/过期治理 | 测量请求量、返回体、恢复耗时和内存趋势后优化热点 |
| 权限与缓存归属 | 身份/会话归属、鉴权失败停止相关请求、敏感详情过滤、分享和文件边界 | 核对退出/换账号/撤权后的缓存和请求处理，不以缓存提速绕过授权 |

可优化项是候选清单，不是已完成的收益，也不要求无差别重写。优先级为：P0 保留可靠性和弱网效果 → P1 优化状态、输入、阅读与审批 → P2 根据测量优化性能和局部视觉细节。全量虚拟列表、附件断点续传、自动升级和整站视觉重做不是默认交付项。

弱网及性能验收补充：

- [ ] 覆盖高延迟、带宽受限、间歇失败、断网恢复、代理返回 HTML 错误、SSE 静默断开和超时。
- [ ] 覆盖手机切后台/回前台、刷新与 PWA 重开、快速切会话、服务重启、缓存过期和浏览器存储不可用。
- [x] 验证可用内容不被清空、草稿不被异步覆盖、不重复执行、阅读位置不被抢走、恢复请求有界，权限检查仍生效。
- [x] 区分离线缓存展示、纯文本待发送和在线执行：断网不保证能取得新历史或上传文件，缓存也不等于完整会话备份。
- [ ] 在相同视口、主题、数据量、网络与运行环境下对比首屏可用时间、会话切换/恢复耗时、长任务、请求量、返回字节和内存趋势。先建立基线再确定阈值；没有测量不能声称性能提升。
